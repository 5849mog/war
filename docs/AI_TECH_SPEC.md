# AI、战斗引擎与技术交接规格 v0.4

本规格给开发者定义**实现边界与可验证行为**，不要求使用某一具体代码实现。固定 2.5D 斜视镜头和美术基调已按 [美术与镜头方向](VISUAL_DIRECTION.md) 确认，底层仍为二维格子模拟。首发平台尚待确认；若设计者之后改变平台或镜头，先修订本文件与路线图。

## 1. 推荐技术方案

- 前端：TypeScript + Vite；游戏画布优先评估 Phaser 的 2D 渲染、输入、资源加载和音频能力；菜单与建筑详情使用普通 HTML/CSS 层，保留手机系统字体、无障碍标签和可伸缩布局。
- 纯规则层：不依赖 Phaser、浏览器 DOM 或真实时钟的 TypeScript 模块。地图、战斗、AI、金币和存档结构都可以在 Node 测试环境运行。渲染层只订阅状态和事件，绝不决定命中、死亡、寻路或扣费。
- 存档：IndexedDB；一份完整版本化的玩家快照事务写入，并保留最近一份有效备份。若浏览器不支持或存储被拒绝，提示玩家并提供手动导出/导入，不假装已经保存。
- 测试：纯规则单元和场景测试可用 Vitest；关键手机触控流程、刷新恢复和横竖屏提示用浏览器端到端测试。安装依赖时以官方兼容版本为准，锁定依赖并提交锁文件，避免照抄文档时的旧版本号。

官方参考：[Phaser 入门与模板](https://docs.phaser.io/phaser/getting-started/project-templates)、[Vite 模板](https://vite.dev/guide/)、[Vitest 指南](https://vitest.dev/guide/)、[Playwright 文档](https://playwright.dev/docs/intro)。这些链接供开发者核对当前 API；本设计不要求固定库版本。

建议目录责任，不要求完全照搬命名：

```text
src/
  config/       建筑、兵种、AI 难度和经济表；运行前校验
  sim/          固定步长战斗、碰撞、伤害、路径、胜负；无 UI 依赖
  ai/           布局生成、进攻部署计划、目标估值
  campaign/     基地蓝图、金币、解锁、升级与阵容
  persistence/  存档版本、事务、迁移、导入导出
  game/         画面、动画、声音、触控坐标转换
  ui/           菜单、建造编辑器、配兵、战报
  tests/        规则测试、固定种子对战、移动端流程
assets/         自有或已获许可的图片、音频、字体及来源记录
```

## 2. 状态、命令和确定性

唯一真实来源是纯数据状态。至少区分：

| 对象 | 关键字段 | 约束 |
| --- | --- | --- |
| `PlayerSave` | `schemaVersion`、金币、核心等级、基地蓝图、解锁、编队、设置、已完成挑战 | 持久化，不存正在被打的临时 HP |
| `BaseBlueprint` | 地图版本、建筑清单、每栋 ID / 类型 / 等级 / 坐标 / `paidCost` | 不能重叠、越界或突破数量上限 |
| `BattleState` | 种子、tick、所有单位和建筑的临时 HP/位置/冷却、弹道、部署库存、累计破坏权重、结果 | 每一帧由模拟命令推进，不回写蓝图 |
| `Command` | tick、玩家或 AI 来源、部署兵种/格、暂停、结束等 | 校验合法才应用；无效命令返回原因 |
| `BattleEvent` | tick、事件类型、实体 ID、来源、数值 | 渲染动画、战报和调试轨迹复用 |

模拟以 **50 ms 固定步长（20 tick/秒）**运行。渲染帧率与模拟解耦；2×速度执行两倍数量的完整 tick，不把单步时间改为 100 ms。规则层不读 `Date.now()`、浏览器帧间隔或未注入的随机数。每局持有种子和确定性的 PRNG；遍历对象时按稳定 ID 排序，同一 tick 多命中按预定顺序处理。输入日志 + 初始蓝图 + 版本化参数 + 种子应能重放同一战斗结果。

建议更新顺序：接收并校验该 tick 命令 → AI 意图 → 路径与移动 → 单位和炮台发射 → 已到达弹道结算 → 同 tick 伤害合并与移除实体 → 更新通行图和破坏权重 → 判定终局 → 产生事件。开发时应在测试中固定具体顺序；不能让绘制循环调用伤害逻辑。一次终局只能生成一份奖励事务。

## 3. 地图与寻路合同

逻辑格与世界坐标分开。所有建造、部署、移动、射程转换使用统一坐标工具；固定斜视时指针先经**屏幕到世界的逆投影**再投影到逻辑格。占地采用整数格矩形，射程用浮点位置计算。建筑阻挡矩形与其地面基座一致，建筑上部的视觉体积不扩大逻辑碰撞。遮挡、深度排序、选中后透明处理与手机触控见 [美术与镜头方向](VISUAL_DIRECTION.md#4-镜头投影和交互建议)。

使用带权 A* 或同等路径算法：空地移动代价 = 距离；可破坏墙作为「需要先攻击」的可选通路，其代价包括预估破墙时间、炮台危险暴露和路线长度；不可破坏建筑本体始终不可穿过，攻击目标选其周边可站位格。为单位的射程和墙体倍率计算不同路径成本，不能给所有兵种同一条穿墙捷径。城墙失效后增量更新通行图；重算加节流，例如目标改变立即重算、其余最多每 10 tick 定期检查。没有移动进展达到阈值时触发一次诊断性重算并记录原因，不能无限循环。

碰撞与选择：八方向可以走，但斜向若两个正交邻格都阻挡则不可走；速度按真实距离计，不因斜走更快。单位攻击建筑时用单位中心到建筑占地边界的最近距离，避免 2×2 或 3×3 建筑被中心距离错误地判成近战永远打不到。近战在通路可抵达且距离满足规则时攻击；远程按距离和射程决定。塔越墙射击，规则见 [GAME_RULES](GAME_RULES.md)。

## 4. AI 对手：三个层次

### A. AI 设计防御基地

每档至少 3 个可选**人工设计的布局模板**，用种子在允许格内有限变体，不靠完全随机堆砌，见 [九种关卡原型与三张坐标基准](TACTICS_AND_LEVELS.md#4-九种-ai-基地原型)。轻松：核心 L1、箭塔 1、机枪台 1、木墙约 12 段；标准：核心 L2、箭塔 2、机枪台 1、火炮台 1、木/石墙约 24 段；挑战：核心 L3、箭塔 3、机枪台 2、火炮台 2、混合墙约 40 段。模板中的塔等级不得超过核心等级，建造数量符合玩家同级上限，军营可作为普通可摧毁目标。三档的具体配置可随平衡调整，但不能暗改射程或隐身炮台。

模板校验：所有建筑合法、不重叠、部署环清空、核心存在、可从部署环走到至少一个可攻击点；围死基地必须存在能攻击并破坏的墙段。每个模板记录版本和种子；玩家点击「重试同一基地」复用版本与种子，点击「换一张地图」才更换。

### B. AI 控制防御炮台

AI 在统一战斗模拟中使用第 3 节炮台的寻敌规则、冷却、盲区和弹道。它不根据玩家手指尚未确认的放置预览做反应，不提前知道即将部署的位置。炮台之间不共享额外视野或无条件转火；难度来自布局和允许的建筑组合，不靠缩短 AI 冷却作弊。

### C. AI 率兵进攻玩家基地

防守测试在 MVP 中提供：AI 的人口上限等于当前玩家军营上限（16 / 24 / 32），以同样兵种属性从外环部署；玩家只能观察与查看战报，不能战斗中移动建筑。AI 分析的是开战时可见基地蓝图、炮台公开射程和已发生的战斗事件，不预知随机结果。进攻步骤：

1. **侦察**：把外环分成 8 个候选进入区域，估计每区到核心及高威胁炮台的路径长度、墙体突破时间、沿路炮火累计暴露、可部署空间。
2. **配兵**：根据墙密度与炮台比例，在同一人口预算内配置铁卫、破垒工、迅击者、巡卫；第二阶段才加入弩手和榴弹手。优先保证至少一个能破墙的单位；AI 不能部署玩家尚未解锁、测试规格未允许的兵种。
3. **选入口**：用可调权重计算 `收益 = 核心/炮台价值 - 行进风险 - 破墙耗时`，选择高分区域。种子只在同分或近分时作可复现的变化，不能完全随机送兵。
4. **分批部署**：先部署承伤单位，间隔数 tick 再部署破墙与输出，留少量人口作预备队；每次命令必须通过与玩家同一部署校验。
5. **重规划**：目标被毁、通路出现、主力损失或 15 秒无进展时重新评估一次；冷却防止每 tick 切换入口。若场上单位全灭但仍有部署库存，立即尝试部署预备队；库存用尽或超时才按统一规则结算。

不要求 AI 深度学习或联网服务。AI 决策日志须记录候选入口得分、选择原因、阵容、重规划触发原因，便于设计者发现「AI 很笨」究竟是权重还是寻路问题。防守测试金币不变；日后做正式防守挑战再单独定义奖励。

## 5. 难度与可解释的平衡

难度旋钮优先调整**基地模板、塔和墙材组合、进攻 AI 的候选评估质量与编队**。禁用难度专属隐性攻击倍率、额外人口或无视碰撞。界面给玩家列出难度的大致构成。AI 可有可复现的战术误差：轻松只看入口距离与粗略炮火，标准兼顾破墙成本，挑战综合危险与目标价值；但三档的单位和建筑属性表一致。

平衡初验：用固定种子与示例基地批量运行至少 30 场，每档检查胜率趋势、平均星级、时长、墙体被攻击频率和三塔使用率。目标是新手阵容能从轻松档学到赢法，标准档需要调整阵容，挑战档需要有针对性的突破；具体胜率不应在没有试玩数据时写死。任何单塔或单兵种长期压过其余选项，应反馈到配置表并记录变更原因。

## 6. 金币事务、存档与版本

金币、基地蓝图和解锁进度一次事务更新。操作流程：读取版本 → 校验余额/等级/占地/上限 → 构造新快照 → 持久化成功 → 更新 UI；写入失败时不显示升级成功、不减少可见金币。战斗奖励采用唯一 battle ID 防重复领取。删除建筑的返还从该实体 `paidCost` 计算，不能由当前价格反推；历史配置调价不改变玩家已付金额。

存档至少包含 `schemaVersion`、内容配置版本、创建时间、最后写入时间、校验信息。加载时验证字段范围、实体类型、坐标、唯一 ID、余额非负、核心和军营存在；旧版按显式迁移链升级；无法迁移则保留原数据和备份，显示导出/重置选项。玩家手动导入前预览版本和将被替换的进度并确认。不要存储不必要的个人数据。

## 7. 移动端性能与体验

基准设备以普通手机浏览器为目标：28×28 格、最多 60 个防御实体（L3 上限：核心、军营、10 座炮台、48 段墙）和 32 人口单位时，战斗画面目标 30 FPS 以上；模拟 20 tick/秒应稳定，掉帧时追赶 tick 有上限且暂停/恢复不跳过关键结算。性能数据在真实手机浏览器采集，不用桌面高性能结果替代。地图地块、城墙连接与静态底图应批量绘制；战斗事件触发动画，视觉粒子不进入碰撞判定。

首次加载先显示进度及可交互状态；资源压缩与按需加载，战斗中不临时下载决定规则的配置。横屏是推荐布局；竖屏提示旋转并保留进度，不能丢失未确认编辑。适配安全区域、触控缩放、屏幕阅读辅助文字、静音、降低动画强度选项。指针手势与 UI 面板须防止事件穿透造成误部署。

## 8. 测试矩阵与出错时的证据

| 层次 | 必须验证的行为 |
| --- | --- |
| 参数校验 | 所有价格非负、HP > 0、射程合法、升级链无跳级、模板不超上限 |
| 规则单测 | 三塔目标和克制、盲区、飞行中炮弹、四墙升级、批量扣费、星级边界、金币一次性发放 |
| 寻路场景 | 封闭石墙、角落斜切、多点突破、墙被毁瞬间、目标同时消失、32 人口拥挤 |
| AI 场景 | 三档模板合法、同种子同决策、入口选择有因可查、无进展后重规划、AI 不越界部署 |
| 重放 | 相同参数版本 + 初始状态 + 种子 + 命令日志生成相同结算摘要；1×/2×一致 |
| 存档 | 升级时刷新、重复结算、旧版迁移、损坏存档、导出导入与无存储权限 |
| 端到端 | 触屏建塔、拖墙、升级、配兵、侦察、部署、暂停、结算、重启恢复、防守测试 |

失败日志至少附：内容版本、存档模式、种子、tick、命令序列、触发的 AI 选择原因、设备/浏览器和可复现步骤。发布构建不应在战报中泄露完整内部调试日志，但可提供开发模式导出。静态检查、测试、生产构建通过后才能进入人工试玩验收。

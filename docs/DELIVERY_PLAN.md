# 开发路线、验收与设计决策 v0.4

这份路线是给下一位负责写代码的 AI 的施工顺序。**当前阶段只完成设计文档；不应宣称游戏已经实现。** 每个里程碑完成后提供可打开的演示、自动化结果、手机实测截图或录屏、已知问题与下一阶段风险，让设计者能逐步验收。

## 1. 工作方式

1. 开始编码前，阅读 README 和所有 `docs/` 文件，整理不一致之处；优先把「待确认」问题交给设计者，保留推荐默认值以免无人能继续推进。
2. 每次只交付一个可玩的纵向切片，不先堆满所有 UI 或数值；功能完成以本表的验收为准。
3. 规则在配置中声明，模拟引擎独立，UI 不持有经济或战斗真相；移动端操作和存档从第一阶段纳入设计。
4. 重大改动先写设计变更：旧规则、新规则、受影响数据、迁移和测试；获得设计者确认后再改。不在实现中偷偷增加付费、在线服务或沿用他作素材。
5. 阶段提交要可回退。修改文件有明确职责，避免把游戏塞进一个巨型 HTML 或一个无法测试的主文件。

## 2. 里程碑

| 阶段 | 可交付切片 | 验收条件 | 暂不做 |
| --- | --- | --- | --- |
| M0 基础 | 项目骨架、移动端空地图、格子坐标与斜视样板、参数校验、纯模拟 tick、存档原型 | 手机上能平移缩放并经逆投影准确点选格；深度排序无明显错误；同种子固定步进同结果；刷新恢复初始基地 | 完整炮台、复杂美术 |
| M1 建造经济 | 核心、军营、三塔和四墙的放置、移动、出售、升级与预览 | 所有占地/余额/上限校验有效；批量升级原子扣费；刷新无金币错账；材质一眼可辨 | 战斗 AI |
| M2 战斗纵切 | 先做巡卫、箭塔、木墙、单图、部署、寻路、伤害、倒计时、星级和战报 | 一局能从侦察打到结算；边界测试通过；1×/2×结算一致 | 其他塔和高级兵种 |
| M3 完整 MVP 战斗 | 机枪台、火炮台、铁卫、迅击者、破垒工、每档 3 张 AI 布局和完整金币奖励 | 三塔功能差异明显；封闭墙也可突破；九张 AI 布局无非法坐标；战斗不软锁 | 两种进阶兵种 |
| M4 AI 攻打玩家 | 防守测试、AI 分批部署与重规划、战报原因记录 | AI 遵守人口/部署/伤害规则；玩家改变防线能影响结果；重试同种子可复现 | 防守金币奖励 |
| M5 产品化 | 按视觉规范制作原创美术和音效、引导、设置、导入导出、完整手机体验、构建 | 三塔四墙缩到整图仍易区分；遮挡可处理；目标手机浏览器稳定运行，测试矩阵通过，初玩者能独立完成一轮建造与攻防 | 在线 PvP |
| M6 扩展 | 弩手、榴弹手、地形与额外挑战、正式防守进度 | 新单位有清晰用途、配置和测试；旧存档安全迁移 | 依赖未确定的多人系统 |

M0–M4 是玩法 MVP，M5 是可公开试玩的首版门槛。可以调整阶段数量，但不能以「AI 有行动动画」代替 AI 行为验收，也不能以桌面调试正常代替手机验收。

## 3. 对开发 AI 的明确交付要求

每个阶段的 PR 或交付说明至少包含：

- **用户可见变化**：从哪个页面进入、能做什么、预期反馈是什么；附手机屏幕尺寸的截图/录屏。
- **规则变更**：数值配置 diff、经济和胜负变化、与本设计文档的差异及原因。
- **验证记录**：运行的检查命令、自动化场景、至少一次实机/移动仿真路径，失败时的种子和复现步骤。
- **遗留问题**：明确是阻塞发布、影响平衡还是可稍后处理；不要把重大失败埋在说明结尾。
- **资料更新**：README 使用方式、已实现清单、存档版本变更、素材许可清单。未实现内容继续留在文档中标记状态。

推荐任务拆分：配置与类型 → 纯战斗引擎 → 地图和碰撞 → 建造事务 → UI 与触控 → 塔和单位 → AI 模板 → AI 主动进攻 → 战报 → 存档迁移 → 美术与性能。每块均要求有清晰输入/输出和最小场景测试。

## 4. 设计与测试验收清单

### 一局完整体验

- [ ] 新玩家首次进入看到已放置的核心、军营、箭塔和 12 段木墙，金币为 2,500。
- [ ] 玩家能预览并放置火炮台、机枪台、箭塔；三者在战斗中呈现不同的目标、频率、射程和范围效果。
- [ ] 玩家能连接城墙、选中多段逐级升级；木 400、石 950、铁 1800、复合 3100 HP 按每段生效。
- [ ] 建造和升级价格与预览完全一致；扣费失败时布局与余额不变。
- [ ] 配兵人口不超军营上限，单位从地图外环部署，有墙时能选择合理突破口。
- [ ] AI 基地合法、三档难度可辨、炮台决策可解释；可重试同一布局。
- [ ] 3 分钟结算星级、破坏率和金币；结果明确，重复打开战报不重复发奖。
- [ ] AI 能从外环攻打玩家基地，遵守同样的人口和战斗规则，并展示入侵方向与结果。
- [ ] 刷新/重启后基地和金币仍在；防守测试不会永久损坏基地。

### 发布前质量门槛

- [ ] 规则测试、AI 场景、重放一致性、存档迁移、手机端到端流程通过。
- [ ] 普通手机浏览器在规定规模下目标 ≥30 FPS，长时间战斗不持续积累实体或明显卡顿。
- [ ] 无卡死、无限寻路、单位落在非法位置、负金币、重复奖励、丢档、按钮误触导致的意外部署。
- [ ] 关键交互有声音关闭、动画减弱、颜色以外的区分手段与可读文字。
- [ ] 美术、音乐和字体都有可追溯授权或原创记录，未挪用其他游戏资产。

## 5. 待确认的设计决策

这些是草案中的**默认假设，不是用户已同意的结论**。设计者回复后更新本表、相关规则和版号，再让开发 AI 固定实现方向。

| 编号 | 问题 | 推荐默认值 | 若改选会影响 | 状态 |
| --- | --- | --- | --- | --- |
| D01 | 首发手机浏览器、电脑浏览器还是桌面安装包？ | 手机浏览器 | UI 手势、纵横屏、发布方式、性能预算 | 待确认 |
| D02 | 进攻 AI 基地、防守 AI 来袭，还是双方实时建造对战为主？ | 异步攻防，两种单机模式 | 战斗时序、服务器需求、AI 架构 | 待确认 |
| D03 | 2D 俯视、固定 2.5D 斜视还是自由 3D？ | 固定 2.5D 斜视，底层二维规则 | 美术量、遮挡、坐标、引擎选择 | 已确认 |
| D04 | 整体美术观感？ | 明快、立体、夸张的卡通奇幻，所有资产原创 | 造型、材质、动效、声音 | 已确认方向 |
| D05 | 首版重策略还是重爽快？希望每场多长？ | 2–4 分钟，策略清楚但操作轻 | 兵种速度、场地、数值和 AI | 待确认 |
| D06 | 是否把防守 AI 来袭做成正式有奖模式？ | 首版仅无金币防守测试 | 奖励循环、刷取设计、存档 | 待确认 |
| D07 | 游戏最终名称？ | WAR 暂定名 | Logo、仓库说明和发布素材 | 待确认 |
| D08 | 具体世界观与角色设定？ | 奇幻工匠城邦作为提案 | 兵种命名、建筑细节、叙事 | 待确认 |

优先回答 **D01–D02** 中尚未确定的平台和对战方式；D03 镜头、D04 美术观感已确认，D05–D08 可以在规则切片验证后继续讨论。若用户提出新的想法，先评估是否改变核心循环、是否应该进入 MVP，再修文档，不靠开发 AI 临场猜测。
